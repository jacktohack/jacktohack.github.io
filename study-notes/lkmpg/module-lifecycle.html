Kernel Module Lifecycle

Created 29 September 2026 · Last edited 29 September 2026

This note explains where Linux kernel modules run, how Kbuild turns source into a loadable module, and how initialization and cleanup define its lifecycle. It also covers module parameters, kernel-build compatibility, and the tools and logs used to verify loading and removal in a QEMU guest.

1. A module adds code and data, but it is not a process

1.1 A loaded module becomes part of the running kernel

A kernel module is a file containing code and data that the kernel can load when needed. The filename normally ends in .ko, meaning kernel object.

When the guest kernel loads hello.ko, it places the module's instructions and data in kernel memory. When hello_init() runs, it runs as kernel code, not as an ordinary application. If the module accesses memory it should not, the failure can affect the whole guest kernel rather than just one application.

Built-in code is included in the kernel before boot. A loadable module can be added after boot. Once loaded, both run as kernel code with the same privilege; the module is not isolated from the kernel:

built-in kernel code -> linked into the kernel before boot
loadable module      -> linked separately and added after boot

A monolithic kernel runs core services and drivers together inside the privileged kernel. In a microkernel design, drivers may instead run outside the kernel as separate processes. Linux modules are loaded later, but they still run inside the kernel; loading them does not turn Linux into a microkernel.

1.2 A module has no PID, private stack, or userspace heap

These terms must not be mixed:

  • A program is executable code stored in a file.
  • A process is a running program instance with resources such as open files and a userspace address space—the range of memory addresses that the process can use.
  • A task or thread is an execution unit selected by the scheduler, the kernel component that chooses which task runs on a CPU. Linux represents each task with struct task_struct.
  • A kernel thread is a schedulable task that performs kernel work without a normal userspace address space.
  • A kernel module is loadable kernel code and data. It is not scheduled independently and has no PID (process identifier) of its own.

The .ko file contains the module’s compiled instructions and data. It organizes them into sections—named groups of related content. The data sections include:

  • .rodata: read-only data;
  • .data: initialized writable data;
  • .bss: writable data that starts as zero.

A stack holds temporary information while a function runs, such as return information and local variables. A module has no stack of its own because it is not a task. When a module function runs, it uses the kernel stack available to the task or interrupt path that called it.

A module has no private heap like a userspace process. If it needs memory while running, it can ask the kernel to allocate some with kmalloc() and release it with kfree() when finished. This allocated memory is separate from the module’s .data and .bss sections.

1.3 Module functions run in the context that calls them

An execution context means the circumstances in which the CPU is currently executing kernel code. For this note, the important examples are:

  • process context: a userspace task entered the kernel, for example through a system call;
  • kernel-thread context: a kernel thread is performing work;
  • interrupt context: the kernel is responding to a hardware interrupt.

A module remains passive until one of these paths calls its code:

userspace task -> system call -----> module callback
kernel thread ---------------------> module callback
hardware interrupt ----------------> module interrupt handler

A system call is a controlled request through which a userspace task enters the kernel for a service. This changes the CPU from user mode to kernel mode, but it does not necessarily cause a context switch, in which the scheduler stops one task and runs another. The same task can enter the kernel, run a module callback, and return to userspace.

2. Module experiments run in a separate QEMU guest kernel

2.1 hello.ko runs in the guest kernel, not host userspace

The test environment used this hierarchy:

host operating system
└── QEMU process
    └── virtual hardware
        └── guest Linux
            ├── guest userspace: BusyBox shell and commands
            └── guest kernel: hello.ko runs here

QEMU is a host userspace program that provides virtual hardware. BusyBox is a compact collection of userspace commands inside the guest. Neither one is the module's execution environment: hello.ko runs in the guest kernel.

A module crash therefore normally damages the disposable guest rather than the host kernel.

2.2 Guest setup: boot files, debugging symbols, and file sharing

The environment contains several artifacts:

  • bzImage: the bootable guest-kernel image loaded by QEMU;
  • vmlinux: the linked kernel file used by a debugger to relate kernel addresses to function names and source lines;
  • initramfs: an archive that supplies the guest's initial root filesystem;
  • BusyBox: the executable that supplies the guest shell and basic commands;
  • 9p virtfs: a file-sharing mechanism that makes a host directory visible inside the guest.

The shared directory only makes hello.ko visible in the guest. It does not load the module. Loading begins when insmod makes a request to the guest kernel.

2.3 The target kernel, not the compiler's location, determines compatibility

The compiler ran on the Linux host, but the resulting module ran in the guest. Therefore the module had to be built against the guest kernel's prepared build directory.

The kernel source tree contains the files used to build Linux. The configuration records choices for that build: a feature can be built in (y), built as a module (m), or left out. Preparing the build uses those choices to create the headers and other generated files an external module needs. The module therefore needs the prepared build for its target kernel, not just a source tree with the right version number.

kernel source tree + selected configuration
    -> preparation creates the kernel build directory
       -> KDIR selects this directory for the module build

compiler runs on:  Linux host
module runs in:    QEMU guest kernel

The build explicitly selected the prepared guest-kernel build directory:

make KDIR=/home/ubuntu/lkmpg/devtools/.cache/kernel-build

Without that override, /lib/modules/$(uname -r)/build would describe the host kernel because make was running on the host. A module can compile successfully for that kernel and still be rejected by the guest because the loader checks target-build compatibility, as Section 7 explains.

3. Kbuild turns hello.c into a loadable hello.ko

3.1 Headers expose interfaces; they are not separately linked libraries

An interface is an agreed way for one piece of code to use another. For example, hello.c uses pr_info("Hello world!\n") to request kernel logging. The kernel headers tell the compiler how to use pr_info(); the module does not contain the whole logging implementation.

Before C is compiled, the preprocessor processes #include directives and expands macros. Headers provide declarations, types, and macros needed to use an interface. Here, <linux/printk.h> provides pr_info as a macro; the preprocessor expands its use in hello.c before compilation.

For example:

#include <linux/module.h>
#include <linux/printk.h>

An include path is a directory the preprocessor searches for headers. Kbuild supplies directories from the target kernel tree, so #include <linux/printk.h> finds that kernel's include/linux/printk.h.

Including <linux/printk.h> makes the pr_info macro available; it does not copy the kernel’s logging implementation into hello.ko. The macro expands during the build, and the loaded module uses the kernel’s logging code when it runs.

3.2 ELF objects carry code, data, symbols, and relocations

The build moves through three files:

  • hello.c is the C source you write.
  • hello.o is compiled code and data with some addresses still to resolve.
  • hello.ko is the loadable module Kbuild makes from hello.o, adding information the kernel needs to load it. The kernel fills in remaining addresses when the module loads.

ELF (Executable and Linkable Format) is the file format of both hello.o and hello.ko. It organizes their code, data, and names so build tools can find them. The linker combines the compiled pieces into hello.ko. Some addresses cannot be filled in until the kernel chooses where to place the module when it loads it.

hello.o contains four kinds of information:

  1. machine instructions compiled from functions such as hello_init();
  2. data such as the string "Hello world!\n";
  3. symbols: names recorded for functions or data;
  4. relocations: records of places where an address must be filled in later.

A symbol, an object, and a pointer are different:

  • a symbol is a name recorded for code or data, such as hello_init in hello.o;
  • a C object is a region of memory that holds data. "Hello world!\n" is a string literal stored as an array of characters;
  • a pointer is an address value. In pr_info("Hello world!\n"), the characters are stored in memory, and the logging code uses their address to read them. The address is not the characters themselves.

In module_init(hello_init), the module must identify the function to run when it loads:

  1. Symbol resolution — which function? Match the name hello_init to its compiled function.
  2. Relocation — fixing addresses: When the kernel loads hello.ko, it chooses where to place the module in memory and adjusts references that need its final addresses.
build time: Kbuild links hello.ko; its load-time address is not yet known
load time:  kernel places the module in memory
            -> resolves any remaining references and applies relocations
            -> calls hello_init()

3.3 Kbuild applies kernel rules, and modpost checks module information

An external module (or out-of-tree module) has source outside the kernel source tree, as hello.c does. Kbuild is the kernel's build system. For this module, the Makefile invokes Kbuild with KDIR set to the prepared guest-kernel build directory, so hello.c uses that kernel's headers, configuration, and module build rules instead of being compiled as a standalone C program.

Metadata describes the module rather than doing its main work; MODULE_LICENSE("GPL") in hello.c is an example. After hello.o is compiled and before hello.ko is linked, modpost checks references to kernel symbols and prepares information to include in hello.ko. If symbol versioning is enabled, modpost records the expected versions of kernel symbols used by hello.ko. When loading the module, the kernel compares these with its own versions and rejects a mismatch.

hello.c
    -> compiler and assembler create hello.o
    -> Kbuild and modpost process module information
    -> linker creates hello.ko

An exported symbol is a name for kernel code or data that other modules may use. Module.symvers is a build-time list of exported names and, when symbol versioning is enabled, their cyclic redundancy check (CRC) values. Kbuild records the relevant CRCs in hello.ko; when loading the module, the kernel compares them with its own. Module.symvers does not contain the function code or its memory address.

3.4 The external-module Makefile tells target Kbuild what to build

The module’s Makefile selects hello.o through obj-m and invokes the prepared target kernel’s Kbuild with KDIR and M. KDIR names the prepared kernel build; M names the external module directory. The modules and clean actions build and remove intermediate outputs. Makefile recipe lines begin with a tab.

3.5 Kbuild selects built-in or module output and combines objects

In-tree code lives inside the kernel source tree. For such code, kernel configuration can select three outcomes:

CONFIG_FOO=y      -> obj-y -> include it in the kernel image
CONFIG_FOO=m      -> obj-m -> build it as a module
CONFIG_FOO unset  -> do not build it

A one-file external module needs one module target:

obj-m += hello.o

A module split across multiple source files needs a final module name and a list of input objects:

obj-m += startstop.o
startstop-objs := start.o stop.o

Here start.o and stop.o are linked together to produce startstop.ko.

4. Initialization makes the module usable; cleanup reverses it

4.1 module_init() and module_exit() identify lifecycle callbacks

A callback is a function you write for other code to call later. In hello.c, you write hello_init() and hello_exit(), but you do not call them yourself. module_init() and module_exit() identify them as the functions to run when the kernel loads and unloads the module:

module_init(hello_init);
module_exit(hello_exit);
  • hello_init() is called while the module is being loaded;
  • hello_exit() is called when the kernel removes a successfully loaded module with rmmod. It is not called if hello_init() fails.

The initialization function returns int:

  • 0 means initialization succeeded, so the module becomes live: loaded and available for use;
  • a negative error value means initialization failed, so the module must not become live.

The exit callback returns void, so it provides no success or failure value. The kernel decides whether removal can proceed before calling it.

Older examples define functions literally named init_module() and cleanup_module(). Current code normally uses ordinary function names plus module_init() and module_exit().

The guide’s hello-1.c uses the older fixed names; hello-2.c uses ordinary callback names with module_init() and module_exit(). In the second example, file-scope static keeps those names local to its C file.

4.2 __init and __exit describe lifetime, not which callback is selected

An annotation is an extra marker on a declaration. For example, __init in static int __init hello_init(void) marks the function as initialization code. It affects where that code is placed; module_init(hello_init) separately selects the function to run when the module loads:

Which function does the kernel call?
module_init(hello_init) -> hello_init at load time
module_exit(hello_exit) -> hello_exit at removal time

Where does the build place code or data?
__init     -> function in the initialization section
__initdata -> data in the initialization section
__exit     -> function in the exit section
  • __init code and __initdata are needed only during initialization. The kernel can reclaim their memory afterward; using reclaimed data is a lifetime bug.
  • __exit cleanup code stays available until a loadable module is removed. Built-in code cannot be unloaded, so its exit code is omitted from the kernel image.

The guide’s hello-3.c applies __init, __initdata, and __exit to a variable and two callbacks. Its file-scope static instead restricts their names to that C file.

4.3 File-scope static keeps a name inside one C source file

A translation unit is a .c file as the compiler sees it after preprocessing, including text from its headers. A name has file scope when it is declared outside any function, as hello3_data and the two callbacks are.

At file scope, the C keyword static gives a function or object internal linkage. That means another translation unit cannot refer to the same entity by that name. The hello module uses:

static int __init hello_init(void)
static void __exit hello_exit(void)

module_init() and module_exit() refer to these callbacks in the same .c file. No other source file needs their names, so the functions can remain file-local.

Inside a function, static applies to a local variable instead: its name stays inside that function, but its value persists between calls. A zero-initialized static variable usually goes in .bss; one initialized to a nonzero value usually goes in .data.

Removing file-scope static allows another .c file in the same module to refer to the name if it has a declaration. It does not make the name available to other kernel modules; that requires exporting the symbol.

4.4 Resources need cleanup on initialization failure and removal

Use one example: a driver callback that needs a buffer in memory.

  1. Who does what? A driver handles device requests. A kernel subsystem routes requests to the driver’s registered functions, called callbacks. The buffer is a resource the driver owns.
  2. Initialize: Get the buffer before registering the callback, because registration may let requests reach it.
  3. Remove: Stop new requests, ensure callbacks already using the buffer have finished, then free it. Freeing it earlier could leave a callback using freed memory.
  4. Initialization fails: If setup fails after getting the buffer, release it before returning the error. The exit callback will not run because the module never finished loading.

5. Verifying a module lifecycle with tools and kernel logs

5.1 modinfo, insmod, lsmod, and rmmod have distinct roles

These tools answer different questions about a module:

  1. What metadata is in the file? modinfo hello.ko reads metadata stored in hello.ko; it does not load the module.
  2. Can the kernel load it? insmod path/hello.ko asks the running kernel to load that file.
  3. Is it loaded now? lsmod lists loaded modules using kernel-provided information from /proc/modules. Despite its location under /proc, that file lists modules, not processes.
  4. Can it be removed? rmmod hello asks the kernel to unload the module named hello.

The loaded module name can differ from its filename: hello-1.ko, for example, may appear as hello_1.

5.2 pr_info() writes to the kernel log, not the invoking terminal

pr_info() creates a kernel log record. It does not behave like userspace printf() writing to the current terminal.

pr_info() -> kernel log (ring buffer), not the terminal
           -> dmesg reads messages still in the buffer
           -> a running system journal may save them

The ring buffer has limited space: new messages eventually replace old ones. A callback that runs often should not log on every call.

5.3 Module metadata, licensing, and out-of-tree taint

Module metadata such as MODULE_LICENSE, MODULE_AUTHOR, and MODULE_DESCRIPTION describes a .ko. See the guide’s hello-4.c for an example. modinfo hello.ko reads the module’s metadata without loading it. MODULE_LICENSE("GPL") also allows the module to use kernel symbols reserved for GPL-compatible modules; an absent or incompatible license can cause a separate license-related taint.

A taint is a flag the kernel sets to record a condition that may matter when debugging; it does not mean the kernel is broken. In this run, (O) in lsmod and the loading out-of-tree module taints kernel message mean an out-of-tree module was loaded. This is separate from its GPL-compatible license.

5.4 Build success alone does not prove load, live state, or removal

Kbuild output
    -> proves hello.ko was produced for the selected build target

successful insmod + initialization log
    -> proves the running kernel accepted it and called initialization

lsmod row showing Live
    -> shows the module was live when observed, after initialization completed

successful rmmod + cleanup log
    -> proves cleanup ran during removal

hello.c shows the intended behavior, and the build shows that Kbuild produced hello.ko. Neither proves the guest ran it. The initialization log, lsmod row, and cleanup log provide evidence that the guest loaded, kept, and removed the module.

6. Module parameters: load-time values and sysfs access

The minimal hello.c in the observed experiment has no parameters. The examples below explain the parameter model shown in the LKMPG source.

6.1 A module parameter has a name, type, backing object, and permissions

In the module’s C source, module_param() is a macro, not a system call. It marks a variable as a setting the kernel may fill when loading the module. The insmod program makes the module-loading system call and passes any supplied setting, such as myint=7, to the kernel:

static int myint = 420;
module_param(myint, int, 0644);

The terms mean:

  • backing object: the C object, here myint, that actually stores the value;
  • parameter name: the name accepted in text such as myint=7;
  • type: the rule for converting the text to a C value, here int;
  • permissions: 0644 exposes myint under /sys (sysfs, a kernel-provided view of live settings). After loading, the file’s owner can read or change it; others can read it. This is separate from passing myint=7 to insmod.

During loading:

insmod example.ko myint=7
    -> find parameter metadata for "myint"
    -> parse "7" as int
    -> store 7 in the backing object
    -> call module initialization

If you load the module without myint=..., myint keeps its initial value of 420. If you pass a value that is not an integer, such as myint=abc, the kernel rejects the load before calling the initialization function.

module_param_array() lets a module accept several values in an array and can record how many were supplied. MODULE_PARM_DESC() adds a description that modinfo can display.

The guide’s hello-5.c shows scalar, string, and array parameter declarations. That example was not part of the recorded guest run.

6.2 Parameter permissions control sysfs exposure and access

sysfs is a virtual filesystem usually mounted at /sys. It is called virtual because its entries look like files and directories, but represent live kernel state rather than ordinary files stored on disk. The kernel supplies their contents when they are read.

A parameter permission of 0 allows a load-time assignment but creates no sysfs parameter file. A nonzero mode such as 0644 creates an attribute that its owner may read and write and other users may read. It appears under:

/sys/module/<module-name>/parameters/<parameter-name>

That file is not an independent disk copy. Reading or writing it accesses the live parameter interface connected to the backing object.

6.3 A callback table stores function pointers for custom parameter behavior

A function pointer holds a function’s address so other code can call it later. A C structure groups named fields. Here, struct kernel_param_ops groups two function-pointer fields, .set and .get; an instance of it is an operations table.

static const struct kernel_param_ops watched_ops = {
    .set = watched_set,
    .get = watched_get,
};

Read the example as follows:

  1. struct kernel_param_ops defines the table’s fields; watched_ops is the table object being created.
  2. .set = watched_set stores the address of the function used to set the parameter.
  3. .get = watched_get stores the address of the function used to read the parameter.
  4. static keeps the table’s name in this C file; const prevents changing the table after it is created.

This code stores function addresses; it does not call the functions. The kernel calls them later when the parameter is set or read.

6.4 module_param_cb() connects a name, callbacks, and data

module_param_cb(watched, &watched_ops, &watched, 0644);

In C, & means “address of.” The two uses of watched below have different roles:

  1. watched names the parameter a user can set.
  2. &watched_ops gives the address of the operations table holding the set/get callback pointers.
  3. &watched gives the address of the integer variable that stores its value.
  4. 0644 sets permissions for its sysfs file after loading.

At build time, module_param_cb() creates a struct kernel_param parameter record in the module’s __param section. The linker carries that parameter record into the .ko. It connects the parameter name watched to the separate watched variable and the watched_ops set/get callbacks; creating it does not call them.

Module is built
    module_param_cb(...)
        -> creates a parameter record in __param:
             name: "watched"
             callbacks: watched_ops
             value location: watched

Module loads with watched=7
    kernel finds the parameter record for "watched"
        -> uses watched_ops.set to call watched_set("7", kp), passing the parameter record as kp
             param_set_int("7", kp) follows the parameter record's value address
                 -> stores 7 in the watched variable
             ret == 0, so watched_set logs "watched updated to 7"
        -> calls hello_6_init()
             log "watched starts at 7"

Someone reads the parameter through sysfs
    kernel uses watched_ops.get to call watched_get(buffer, kp), passing the same parameter record as kp
        -> param_get_int(buffer, kp) follows the parameter record's value address
             -> reads watched and writes "7" into buffer
        -> if ret >= 0, watched_get logs "watched was read"

Module is removed
    kernel calls hello_6_exit()
        -> log "Goodbye, world 6"

The kernel supplies kp when it calls either callback. val receives incoming text in the setter; buffer receives outgoing text in the getter. Neither callback runs when module_param_cb() appears in the source.

The guide’s hello-6.c joins custom set/get callbacks to one parameter.

If this LKMPG example were built for the guest as hello-6.ko, these guest commands would set watched to 7 and show its log messages:

insmod /path/to/hello-6.ko watched=7
dmesg | tail

Expected relevant log lines:

watched updated to 7
Hello, world 6
watched starts at 7

The set callback logs first, before hello_6_init() logs the starting value.

7. A module must match the particular kernel build that loads it

The module was built using the guest kernel’s prepared build directory, and that guest successfully loaded it. This shows hello.ko was compatible with that guest kernel.

7.1 Matching kernel version numbers do not guarantee compatibility

A version number such as 6.12.6 is only a label. Two kernels with that number can have different build settings or interfaces. A module built for one may not load into the other.

A successful compile shows that hello.ko was built against the kernel files selected by KDIR; it does not show that another running kernel will accept it. Compatibility means the assumptions used to build the module match the running kernel. For example, if a module expects a structure field at byte 8 but the kernel places it at byte 16, the module could read the wrong data.

7.2 vermagic checks the kernel release and build settings

A .ko contains a version magic (vermagic) string: the kernel release plus other build properties. For example, these commands run in the guest could show:

$ modinfo -F vermagic hello.ko
6.12.6 ...other build properties...
$ uname -r
6.12.6

6.12.6 is only the kernel version number; vermagic also records build settings. When loading the module, the kernel checks the relevant details against its own build. If they differ, it may reject the module with Invalid module format. If they match, this one check passes, but other checks can still prevent loading.

7.3 CONFIG_MODVERSIONS checks per-symbol type CRCs

With CONFIG_MODVERSIONS=y, exported symbols have CRCs derived from their declared types—for a function, this includes its argument and return types. A symbol with such a CRC is called versioned; the CRC is not a kernel release number or a memory address. The target kernel’s Module.symvers lists these CRCs. When building a module, Kbuild records the relevant CRCs in its .ko, not the Module.symvers file itself. At load time, the running kernel compares the recorded CRCs with its own.

For example, suppose a module uses a hypothetical exported function device_read:

module expects:        device_read CRC 0xA1
running kernel has:    device_read CRC 0xB2
result:                mismatch -> reject the module

The kernel checks CRCs for exported symbols the module uses, one symbol at a time. A matching CRC passes that symbol’s check. This check is separate from vermagic; passing both does not guarantee the module will load.

module_layout is a special symbol associated with the kernel’s module data layout, including struct module. The .ko carries an expected CRC for this symbol, not a CRC of the whole module file. At load time, the kernel compares it with its own module_layout CRC. “Disagrees about version of symbol module_layout” means those two CRCs differ; it is not a vermagic mismatch.

7.4 dmesg helps explain an Invalid module format error

If insmod reports Invalid module format, that message alone does not identify the cause:

  1. Read the guest kernel log with dmesg for the specific loader message.
  2. Inspect the .ko with modinfo and check which KDIR was used to build it.
  3. Use the log message to distinguish a vermagic mismatch from a symbol CRC mismatch.
  4. If the module was built for the wrong kernel, rebuild it against the running guest kernel’s prepared build directory.

Some module tools offer force options that bypass selected checks. Do not use them to insert a mismatched module: bypassing a check does not make the module compatible.

8. Recorded experiment: building, loading, and removing hello.ko

8.1 hello.c logs initialization and cleanup

The observed experiment’s hello.c designates two callbacks with observable log messages:

static int __init hello_init(void)
{
    pr_info("Hello world!\n");
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("Bye world!\n");
}

module_init(hello_init);
module_exit(hello_exit);

On load, hello_init() logs “Hello world!”; on removal, hello_exit() logs “Bye world!”.

8.2 Kbuild output records compilation and linking, not loading

The Linux host ran these commands to build a module for the QEMU guest. KDIR points to the guest kernel’s prepared build files:

make clean KDIR=/home/ubuntu/lkmpg/devtools/.cache/kernel-build
make KDIR=/home/ubuntu/lkmpg/devtools/.cache/kernel-build

The second command’s build output included these stages:

CC [M]   hello.o
MODPOST  Module.symvers
CC [M]   hello.mod.o
CC [M]   .module-common.o
LD [M]   hello.ko
Your source: hello.c
    -> CC [M] compiles it into hello.o
    -> MODPOST checks module information and writes Module.symvers
    -> CC [M] compiles two Kbuild-generated pieces
    -> LD [M] links the compiled pieces into hello.ko on disk

Later: insmod asks the guest kernel to load hello.ko

These are progress labels printed by the kernel build system (Kbuild), not commands you typed. CC means compile, LD means link, and [M] marks work on a module. The .o files are compiled object files; .ko is the resulting kernel-module file. Read each line in order:

  1. CC [M] hello.o: compile hello.c into hello.o.
  2. MODPOST Module.symvers: check module and exported-symbol information; Module.symvers is a build-time symbol list, not code linked into hello.ko.
  3. CC [M] hello.mod.o: compile module information generated by Kbuild.
  4. CC [M] .module-common.o: compile another Kbuild-generated piece; this is not another source file you wrote.
  5. LD [M] hello.ko: link the compiled pieces into hello.ko. LD does not mean the kernel loaded the module.

The build produced a file on disk; the guest's separate insmod step shows whether it loaded.

8.3 Guest logs and lsmod show load, live state, and cleanup

The guest reported Linux 6.12.6. The recorded guest run can be read in three steps:

  1. insmod /mnt/lkmpg/module-lifecycle/hello.ko requested a load. The kernel log then showed Hello world!, matching hello_init().
  2. lsmod | grep '^hello' showed hello ... Live ... (O). The module remained loaded after initialization; (O) identifies it as out-of-tree.
  3. rmmod hello requested removal. The kernel log then showed Bye world!, matching hello_exit().

The out-of-tree taint warning came from the kernel, not hello.c.
